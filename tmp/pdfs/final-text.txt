01 Project introduction
inBox is a full-stack e-commerce application that brings shopping, order management, merchant operations and seller
governance into one browser-based platform. Customers can browse a catalog, search and filter products, choose
variants, save favorites, manage a cart and address book, obtain a server-calculated quote and place orders. Merchants
receive a dedicated operations panel, while super administrators review seller applications and govern platform access.
The project addresses a common commerce problem: product discovery, pricing, stock, customer accounts and
fulfillment must remain consistent across multiple screens and user roles. Its architecture separates a React
presentation layer from an Express API and PostgreSQL persistence. Prisma describes the relational model and
supplies typed database access. The backend recalculates monetary values from stored product prices and reserves
inventory through conditional updates inside transactions.
Business purpose and intended users
For shoppers, the platform provides a journey from product discovery to order tracking. For merchants, it centralizes
inventory, imagery, fulfillment queues, customer information and revenue indicators. For platform operators, it provides
seller application review, approval, rejection, suspension and administrator governance. Managers and judges can
evaluate both the implemented workflows and the engineering evidence behind them.
Implemented scope
The interface includes a storefront, catalog, product details, cart, wishlist, checkout, order success and tracking, order
history, profile, login, seller onboarding, merchant dashboard and super-admin dashboard. English, German and Dutch
translation dictionaries are present. Stripe hosted checkout and Cash on Delivery use separate payment paths.
Cloudinary supports product-image uploads when configured.
Engineering approach
The application uses browser-history navigation, React contexts for shared state, a fetch-based API client,
cookie-backed sessions, role checks, REST-style modules, database constraints, and unit, mocked-service,
component, browser and load-testing tools. The source includes Docker configurations, seed and backup utilities, and a
GitHub Actions verification workflow.
Evaluation position
The implementation is suitable for a detailed project demonstration and engineering review. This report does not certify
a production release: source inspection found payment-trust and seller-scope gaps, schema-to-migration drift and
incomplete recovery evidence. Fresh test outcomes and older results are separated so reviewers can judge the actual
state of the project.
Evidence: src/App.tsx; server/app.ts; prisma/schema.prisma; package.json; server/modules/*

Request and data flow
The browser calls relative /api URLs with credentials included. In development, Vite on port 3000 proxies traffic to
Express on port 4000. Express creates/propagates x-request-id, logs duration/status, enforces request policy, parses
cookies and bounded bodies, and dispatches routers. Prisma accesses PostgreSQL. Most successful responses use a
data envelope; errors use an error object.
Deployment shape
Express serves an existing dist/ directory with an SPA fallback. Docker builds UI and backend in a builder stage and
runs Node as an unprivileged user. This is a modular monolith; no separate microservices, queue, Redis cache or
background worker was found.
Documentation corrections: navigation uses pushState/popstate, not React Router; the API client uses fetch, not Axios. Helmet is neither
listed nor mounted. The @google/genai dependency does not establish an implemented AI workflow.

Roles and seller lifecycle
Database roles are CUSTOMER, ADMIN and SUPER_ADMIN; UI values are customer, admin and superadmin.
SellerStatus is separate: PENDING, APPROVED, REJECTED or SUSPENDED. Approval promotes the linked user to
ADMIN. Suspension archives products matched by specifications.sellerId or specifications.sellerEmail.
What the metrics represent
Merchant paid revenue sums that merchant's item totals from paid orders; it is not net settlement revenue and does not
allocate order-level tax, shipping or discounts. Low stock means stock <=10 for unarchived products. The analytics tab
contains fixed monthly revenue bars and a fixed +24% YoY label. Present these as sample UI data, not measured
business results.
Seller scope is incomplete: order status/payment mutations check admin role without a merchant-ownership condition; matching order lists
include every order item. Suspension is not checked by requireAuth/requireAdmin. These are release-priority findings, not verified
protections.

07 Commerce workflows and rules
Browse, quote and checkout
Catalog search uses case-insensitive contains over product name, description and brand, with category equality
filtering. Paging defaults to 50 and caps at 100. Sort values: featured, price_asc, price_desc, rating, newest. This is
database filtering, not a dedicated full-text search engine.
The quote service accepts up to 100 items with positive safe-integer quantities. It loads stored prices, excludes
missing/archived/out-of-stock products, caps quantity to stock and returns warnings. Coupons support percentage
discounts, minimum spend, optional caps, free shipping and usage limits. The schema has no coupon-expiry or
fixed-amount-discount field.
RULE
IMPLEMENTATION
Stored money
Integer minor units; serializers also expose major units.
Free/reduced shipping
Subtotal >=7500 minor units ($75), or free-shipping coupon.
Standard shipping
499 minor units below threshold; otherwise 0.
Express shipping
1299 minor units below threshold; otherwise 499.
Tax
Round 8% of max(0, subtotal - discount); application rule, not configurable tax engine.
Total
max(0, subtotal - discount) + delivery + tax; 0 for empty valid quote.
Currency
Order/Stripe creation uses USD. Display controls are not proof of multi-currency settlement.
Inventory and order lifecycle
POST /api/orders recomputes a quote, optionally compares expectedTotalMinor, and associates an idempotency key
with a payload hash. A transaction conditionally decrements stock, records coupon use, writes order/item/address
snapshots and status history, clears ordered cart products and saves the checkout record. Retry the same logical order
with the same key; omitted keys generate new ones.
Stages: Order Placed, Confirmed, Packed, Shipped, Out for Delivery, Delivered. Backward transitions are rejected;
forward jumps are allowed. COD begins Pending, and an admin can collect payment. Stripe uses a separate
pending-order/session flow and signed webhooks. Payment-integrity gaps are in section 21.
Evidence: server/modules/catalog; server/modules/checkout/pricingService.ts; server/modules/orders; server/modules/payments

08 Database design and integrity
The Prisma schema defines 17 PostgreSQL models. IDs are text, generally uuid() defaults; Product.id is supplied by
application/seed code. Media, variants and specifications use JSON. Monetary values use integer minor units. Role and
SellerStatus are enums; payment and fulfillment states are strings enforced by application logic.
AREA
MODELS
Identity and sellers
User, Session, Address, SellerApplication
Catalog and shopping
Product, CartItem, SavedItem, WishlistItem, Review
Checkout and orders
Order, OrderItem, OrderStatusHistory, CheckoutRequest
Marketing
Coupon, CouponRedemption, NewsletterSubscription
Infrastructure
HealthCheck
Keys, ownership and deletion
Unique keys protect user email, session token hash, coupon code, order number and checkout idempotency key.
Cart/saved variants use userId + productId + selectedColor + selectedSize uniqueness. Wishlist is unique per
user/product; Review per product/user. CheckoutRequest.orderId is optional and unique, giving an order at most one
ledger record.
User deletion cascades to sessions, addresses and shopping/review/checkout data, but orders use Restrict. Product
deletion cascades to shopping/review rows and sets historical OrderItem.productId to null. SellerApplication.userId also
uses SetNull. Order items/status history cascade with their order; coupon deletion is restricted by redemptions.
Indexes and snapshots
Indexes cover role, session expiry, owner IDs, category/archive flags, order user/date/status and review product/date.
Shipping addresses and item names/prices are snapshots. CouponRedemption.orderId, SellerApplication.reviewedBy
and OrderStatusHistory.actor are scalar fields, not declared foreign keys.
Migration gap: The only checked-in migration defines Role with CUSTOMER and ADMIN and lacks newer seller application/status
additions. The ER diagrams describe schema.prisma, not a verified live database. A clean installation using only prisma migrate deploy will
not necessarily match the schema; a reviewed follow-up migration is required.
Evidence: prisma/schema.prisma; prisma/migrations/20261019070107_init_commerce_schema/migration.sql

14 API contracts and examples
Protocol and envelopes
Ordinary writes use JSON and X-Requested-With: XMLHttpRequest. Browser Origin must match the allowed origin;
non-browser clients without Origin still need the header. The frontend includes credentials and a CSRF cookie token
when available. Session cookie: inbox_session_id. Success usually returns { data: ... }; errors return { error: { code,
message, requestId? } }. Upload and webhook bodies have special formats.
OPERATION
KEY INPUT / OUTPUT
Catalog query
category, search, minPrice, maxPrice, sort, page, pageSize and merchandising flags -> products, total, page,
pageSize, totalPages.
Cart
productId, quantity, selectedColor?, selectedSize?; update quantity by item ID. Merge takes items array.
Quote
items? [{productId, quantity, selectedColor?, selectedSize?}], deliveryMethod?, couponCode? -> totals with Minor
equivalents, warnings, couponError?.
Order create
items?, shippingAddress, deliveryMethod?, paymentMethod?, couponCode?, expectedTotalMinor?, customer
fields; idempotency-key header -> order, replayed? on retry.
Stripe session
items, shippingAddressId or shippingAddress, deliveryMethod?, couponCode? -> sessionId, url, orderNumber.
Order operations
status, note?, trackingNumber? for status PATCH; note? for collection. ID accepts internal ID or orderNumber.
Product write
name, brand, category, description, price, originalPrice, discount, stock, images, colors, sizes, specifications and
feature flags. Price input is major units.
Review
rating, title?, comment -> upserted review and recomputed average.

name?, storeName, legalName?, email, phone, businessAddress, category?, taxId?, description?, password
when linking/creating account.
